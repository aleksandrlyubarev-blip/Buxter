# Buxter BIM Analysis Agent — анализ строительной PDF-документации

Третий слой Buxter MAS. Modeling Agent порождает геометрию, Web Operator
относит её в веб-инструменты, BIM Analysis Agent читает строительную
документацию: отвечает на вопросы об объёмах работ и материалах по
комплекту чертежей в PDF, с проверяемыми источниками для каждого числа.

## Методология: Relational Indexing Workflow

Комплект не анализируется как набор изображений. Сначала строится
реляционный индекс, затем агент отвечает на вопросы, опираясь на индекс и
точечные обращения к страницам.

Приоритет методов извлечения (сверху вниз):

1. Векторный текст и метаданные PDF (pdfplumber, с координатами).
2. Таблицы: ведомости, спецификации, экспликации (`extract_tables`).
3. Размерные линии, марки и выноски, найденные по координатам.
4. Визуальное чтение одного листа или фрагмента (`render_page`,
   pypdfium2) — только в крайнем случае: нет текстового слоя, марка или
   размер распознаны неоднозначно, нужно подтвердить геометрию.

## Слой данных: `pdf_index.py`

- `load_pages` — извлечение текстового слоя каждой страницы с bbox
  каждого слова (`TextSpan`).
- `detect_sheet_metadata` — детекция номера листа, ревизии и дисциплины.
  Сначала сканируется зона штампа (нижняя/правая полоса страницы), чтобы
  ссылка «SEE S-201» в теле чертежа не победила собственный номер листа.
  Поддержаны западная нумерация (S-101, A-201.1, FP-102) и марки ГОСТ
  (КЖ, АР, ОВ… + «Лист N»). Ненайденное поле остаётся пустым — никаких
  значений по умолчанию.
- `find_occurrences` / `cluster_occurrences` — поиск марок с координатами
  и группировка близких фрагментов (марка, разбитая на куски текста,
  считается одним экземпляром). Кластеризация не пересекает границы
  страниц.
- `exclude_zones` — исключение зон легенд, примечаний и типовых узлов из
  подсчёта.
- `write_artifacts` — генерация артефактов проекта (см. ниже) и
  `set-manifest.json` со списком PDF комплекта.

Страница, чей текстовый слой короче `MIN_TEXT_CHARS`, помечается как
кандидат на OCR/визуальную проверку — она не пропускается молча.

## Артефакты проекта (workdir)

| Файл | Назначение | Кто пишет |
|---|---|---|
| `drawings.md` | Мастер-реестр: файл, PDF-страница, лист, название, ревизия, дисциплина, содержимое, связи, статус текстового слоя | индексатор (реестр), агент (название/связи) |
| `objects-database.md` | Объектная база: категория, марка, количество, размеры, материал, источники, метод, надёжность | агент |
| `specs-wiki.md` | База спецификаций: общие примечания, нормы, материалы, допуски, противоречия — каждое правило со ссылкой на источник | агент |
| `notes.md` | Свободные рабочие заметки агента | агент |
| `set-manifest.json` | Список PDF комплекта для `buxter bim ask` без `--pdf` | индексатор |

`buxter bim index` пересоздаёт только реестр; накопленные
`objects-database.md` и `specs-wiki.md` сохраняются между сессиями.

## Агент: `bim_agent.py`

Tool-use loop по образцу Web Operator Agent. Инструменты:

| Tool | Действие |
|---|---|
| `list_sheets` | реестр комплекта |
| `read_page_text` | текстовый слой одной страницы |
| `search_text` | вхождения текста/regex с координатами |
| `count_tag` | кластеризованный подсчёт экземпляров марки |
| `extract_tables` | таблицы одной страницы |
| `render_page` | PNG одного листа для визуального подтверждения |
| `read_artifact` / `write_artifact` | работа с артефактами (whitelist по имени) |
| `finish` | структурированный итог |

Границы безопасности — те же принципы, что в browser-слое:

- запись на диск только в четыре артефакта по точному имени, никакого
  path traversal;
- ошибки извлечения возвращаются модели как `is_error`-результат, а не
  роняют процесс;
- ответ обязан прийти через `finish` со структурой `answer` /
  `reliability` (High|Medium|Low) / `sources` / `unresolved` — свободный
  текст без источников не является результатом.

## Правила достоверности (зашиты в system prompt)

- Номер страницы PDF ≠ номер строительного листа; в источниках
  указываются оба: `[Лист S-101, PDF стр. 4, узел 3]`.
- Марки в легендах, примечаниях и типовых узлах не считаются
  экземплярами; `count_tag` их не исключает — агент обязан выявить эти
  зоны и вычесть их явно.
- Марка на плане не определяет объём: до расчёта 3D-величины требуется
  количество (план) + длина/ширина (размер или ведомость) + третья
  координата (разрез или узел) + материал (ведомость/спецификация).
- Минимум две независимые проверки перед выдачей числа (план ↔
  ведомость, сумма частей, порядок величины, единицы, габариты здания).
- Приоритет при противоречиях: ревизия/addendum → профильная ведомость →
  явный числовой размер → узел/разрез → план → общие примечания →
  измерение по масштабу. Существенные противоречия не разрешаются
  самостоятельно — показываются оба значения.
- Статусы значений: `Extracted` / `Calculated` / `Estimated` /
  `Unresolved`; надёжность `High` / `Medium` / `Low` не скрывается.

## CLI

```bash
pip install -e ".[bim]"

# 1. Индексация комплекта → артефакты в workdir
buxter bim index set1.pdf set2.pdf -w bim/

# 2. Вопросы по комплекту (PDF берутся из манифеста)
buxter bim ask "Сколько фундаментов F1 и какой объём бетона?" -w bim/
```

Настройки: `BUXTER_BIM_WORKDIR` (по умолчанию `./bim`),
`BUXTER_BIM_MAX_STEPS` (60), `BUXTER_BIM_RENDER_DPI` (150).

## Ограничения и дальнейшие шаги

- OCR сканированных листов пока не встроен: страницы без текстового слоя
  помечаются в реестре, агент читает их через `render_page` (мультимодально).
- `extract_tables` опирается на линии разграфки pdfplumber; таблицы без
  рулингов агент читает через `read_page_text`.
- Названия листов — свободный текст; автоматическая детекция ограничена,
  поле заполняет агент при первом чтении листа.
- Дальше: пакетный отчёт «объектная база по всему комплекту», сверка
  ревизий между версиями комплекта, экспорт ведомости объёмов в xlsx.
