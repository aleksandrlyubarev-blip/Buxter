# Buxter на внешней NVIDIA L40 — анализ применимости

Вопрос: что даёт агенту Buxter внешняя (арендованная / вынесенная за пределы
рабочей станции) NVIDIA L40 48 ГБ в задаче помощи инженеру-конструктору.

Все числа ниже делятся на три категории и помечены явно:
**[факт]** — спецификация вендора или прямое чтение кода этого репозитория,
**[расчёт]** — арифметика из фактов (формула приведена),
**[оценка]** — экспертная прикидка, требующая замера (см. §8).

---

## 0. Краткий ответ

**L40 не окупается как замена Claude в контуре рассуждения и не должна туда
ставиться.** Генерация параметрического CAD-скрипта (`buxter draw`) и
рассуждение BIM-агента — это малый объём вызовов с высокой ценой ошибки;
открытые модели, которые физически влезают в 48 ГБ, здесь заметно слабее, а
локальная генерация ещё и медленнее по wall-clock (§3).

**L40 окупается как машина восприятия и геометрии** — там, где у Buxter
сегодня дыра, а не просто «дороговато»:

| Что закрывает L40 | Статус в репозитории сейчас |
|---|---|
| OCR сканированных листов | не реализован — `SheetRecord.needs_ocr` только помечает лист (`pdf_index.py:142`) |
| Детекция графических символов (марки без текста, штриховки, выноски) | невозможна: `find_occurrences` работает только по векторному тексту (`pdf_index.py:286`) |
| Исчерпывающая проверка минимальной толщины | заменена выборкой из 300 точек (`validator.py:65`) |
| Обмер детали по фото | запрещён промптом: «Use the photo for topology, NOT for absolute dimensions» (`prompts.py:47`) |
| Экспресс-FEA / топологическая оптимизация | отсутствует как слой |
| Семантический поиск по нормам и спецификациям | только точное совпадение и regex |

Из них самый ценный для **инженера-конструктора** — четвёртый: L40 переводит
фотографию из «подсказки о форме» в **обмеренную референсную геометрию**, что
снимает главное заявленное ограничение Modeling Agent.

Рекомендация: **гибрид** — L40 в контуре восприятия/геометрии, Claude API в
контуре рассуждения и кодогенерации. Разделение проходит ровно по границе
«много вызовов, дёшево за вызов, открытые модели на паритете» против «мало
вызовов, дорого ошибиться, открытые модели отстают».

Отдельно: если L40 **внешняя в смысле «вне периметра»**, то аргумент
«локальная модель ради конфиденциальности» не работает — см. §6.1, там же
разбор Confidential Computing.

## 1. Аппаратная рамка L40

**[факт]** Ключевое для наших задач:

| Параметр | L40 | Почему важно для Buxter |
|---|---|---|
| VRAM | 48 ГБ GDDR6 с ECC | потолок размера модели и длины контекста (§5) |
| Пропускная способность памяти | 864 ГБ/с | **определяет скорость генерации токенов**, декодинг упирается в память, не в вычисления |
| FP32 | ~90 TFLOPS | геометрия, FEA, фотограмметрия |
| BF16/FP16 Tensor (dense) | ~181 TFLOPS | prefill длинного контекста, OCR, детекторы |
| FP8 | поддерживается (Ada) | позволяет держать 32B-модель в весах ~33 ГБ |
| RT-ядра | 3-е поколение, 142 шт. | трассировка лучей для рендера превью и проверок пересечений |
| NVENC / NVDEC | 3 / 3 | кодирование потока при удалённом GUI и записи прогонов |
| NVLink | **нет**, только PCIe Gen4 x16 | вторая карта масштабируется плохо: обмен идёт через **~31,5 ГБ/с в одну сторону** против 864 ГБ/с внутри карты (§5) |
| Confidential Computing (TEE) | **нет** (только Hopper/Blackwell) | нельзя аттестовать, что хост не читает VRAM — критично для §6.1 |
| TDP | 300 Вт, пассивное охлаждение, 2 слота | только серверное шасси с продувом, не рабочая станция под столом |

Два следствия, которые дальше используются постоянно:

1. **Скорость генерации ≈ пропускная память / размер весов.**
   `[расчёт]` 864 ГБ/с при весах 33 ГБ — теоретический потолок 26 ток/с;
   реально с учётом накладных расходов около 0,7 от потолка → ~18 ток/с.
2. **Скорость prefill ≈ эффективные TFLOPS / (2 × параметры).**
   `[расчёт]` при MFU ~40 % (≈70 эффективных TFLOPS) и модели 32B:
   70·10¹² / (2·32·10⁹) ≈ **1 100 токенов/с** на разбор входного контекста.
   Контекст в 100 тыс. токенов — это полторы минуты только на чтение.

## 2. Профиль нагрузки Buxter: где что упирается

Разбор по модулям репозитория. Колонка «Ускоряется L40» — не «можно ли
запустить на GPU», а «изменится ли что-то содержательно».

| Модуль | Что делает | Упирается в | Ускоряется L40 |
|---|---|---|---|
| `vision.py:119` | 1 мультимодальный вызов Claude → CAD-скрипт | сеть + качество модели | ❌ (см. §3) |
| `runner.py` | `freecadcmd`, ядро OCCT | 1 поток CPU, B-Rep-ядро | ❌ OCCT однопоточное, GPU не использует |
| `fusion_runner.py` | Fusion 360 GUI/subprocess | GUI-сессия, лицензия | ⚠️ только как vGPU-хост для GUI |
| `exporter.py` | проверка наличия файлов | I/O | ❌ |
| `validator.py:65` | watertight/bbox/min-wall по 300 выборкам | CPU, trimesh+rtree | ✅ **качественно**: SDF вместо выборки (§4.3) |
| `browser.py` | headless Chromium | CPU, программный WebGL (SwiftShader) | ✅ веб-вьюеры CAD на WebGL (§4.6) |
| `web_agent.py:236` | цикл tool-use, 40 шагов | сеть + качество модели | ❌ |
| `pdf_index.py:173` | извлечение векторного текста pdfplumber | 1 поток CPU | ⚠️ частично (парсинг PDF — CPU) |
| `pdf_index.py:142` | пометка листов без текстового слоя | — | ✅ **новая функция**: OCR (§4.1) |
| `pdf_index.py:286` | поиск марок по тексту | CPU, тривиально | ✅ **новая функция**: детекция символов (§4.2) |
| `bim_agent.py:407` | растеризация листа в PNG, pypdfium2 | CPU | ⚠️ ускорение есть, но не оно узкое место |
| `bim_agent.py:577` | цикл рассуждения, до 60 шагов | сеть + качество модели | ❌ (см. §3) |

Вывод по таблице: **ни один сегодняшний узкий участок Buxter не лечится
простым переносом на GPU.** CAD-ядро однопоточно по природе, парсинг PDF
упирается в CPU, а модельные вызовы — в сеть и качество. GPU здесь покупает
не ускорение существующего, а **новые слои**, которых в коде нет.

## 3. Сценарий А: перенести LLM на L40 — почему нет

Соблазнительная идея: поднять на L40 открытую модель через vLLM, заменить
`anthropic.messages.create` и убрать счёт за API. Разбор по трём осям.

### 3.1. Качество

`buxter draw` требует одновременно: пространственного рассуждения по фото,
знания FreeCAD/Fusion API, и соблюдения десяти жёстких правил системного
промпта (`prompts.py:5-24`) — включая «ровно один fenced-блок», обязательный
B-Rep вместо Mesh, чтение путей из переменных окружения. Ошибка не мягкая:
скрипт либо не запустится в `freecadcmd`, либо экспортирует пустой STEP.

Модели, которые влезают в 48 ГБ (7B–32B плотных, 70B в 4 битах), на задачах
«длинный код по спецификации с жёсткими ограничениями формата» заметно
уступают фронтирным. `[оценка]` На сборках уровня `samples/miranda-rfv-2u`
(допуски ±0,05 мм, параметризация через `asic_count`) разрыв в доле
скриптов, проходящих `buxter validate`, ожидается кратный, а не в единицах
процентов. Это гипотеза, и она **проверяема существующим инструментом** —
см. §8, там весь смысл в том, чтобы не спорить, а замерить.

### 3.2. Скорость — контринтуитивный результат

Локальная модель **медленнее** по времени до результата, а не быстрее.

`buxter draw`, один вызов, выход ~2 500 токенов скрипта:

| Вариант | Расчёт | Время |
|---|---|---|
| Claude API | сеть + фронтирная инфраструктура | `[оценка]` 40–60 с |
| L40, 32B FP8 | 2 500 / 18 ток/с | `[расчёт]` **~140 с** |
| L40, 14B FP8 | 2 500 / 40 ток/с | `[расчёт]` ~63 с |
| L40, 32B INT4 | 2 500 / 33 ток/с | `[расчёт]` ~76 с |

`buxter bim ask` хуже на порядок, потому что это цикл до 60 шагов
(`config.py:38`). При 25 шагах, дельте контекста ~2 тыс. токенов на шаг и
ответе ~300 токенов на шаг:

`[расчёт]` 25 × (2 000/1 100 + 300/18) ≈ 25 × 18,5 с ≈ **7,7 минуты** против
`[оценка]` 1,5–3 минут через API.

Критично: без **автоматического кэширования префикса** (vLLM APC) каждый шаг
переразбирал бы весь растущий контекст, и цифра выросла бы до десятков минут.
Для агентных циклов APC — не опция, а обязательное условие.

### 3.3. Экономика

`[оценка]` Профиль одного инженера-конструктора: 30 прогонов `draw`/`retry`,
8 вопросов `bim ask`, 4 задачи `web` в день.

`[расчёт]` По тарифам Sonnet ($3/$15 за млн токенов, чтение кэша $0,30/млн):

| Операция | Входные токены | Выход | Цена за вызов | В день |
|---|---|---|---|---|
| `draw` | ~3,2 тыс. (промпт 1,5 + фото ~1,5) | ~2,5 тыс. | $0,047 | $1,41 |
| `bim ask` | ~600 тыс. накопительно, 90 % из кэша | ~8 тыс. | $0,46 | $3,70 |
| `web` | ~250 тыс. накопительно, 90 % из кэша | ~4 тыс. | $0,20 | $0,80 |
| | | | **Итого** | **~$6/день** |

≈ **$130 в месяц на инженера** (21 рабочий день) на Sonnet;
на Opus для `draw` — примерно вдвое.

Против этого `[оценка]` стоимость L40: аренда on-demand $0,7–1,2/час →
$540–865/мес при работе 24/7; резерв — $400–600/мес; собственная карта в
сервере — CAPEX $12–15 тыс., то есть $350–420/мес за три года плюс ~360 кВт·ч
в месяц и администрирование.

**Точка безубыточности — 3–5 инженеров**, и только при допущении, что
локальная модель делает ту же работу. Допущение неверно (§3.1). При
утилизации одного инженера карта простаивает: `[расчёт]` 42 вызова в день по
несколько секунд GPU-времени — это **менее 3 % загрузки**.

**Вывод §3: замена API локальной моделью проигрывает по всем трём осям
одновременно.** Это редкий случай, когда решение однозначно.

## 4. Сценарий Б: L40 как машина восприятия и геометрии

Здесь картина обратная: задачи с высоким объёмом, низкой ценой единичной
ошибки и открытыми моделями на паритете с проприетарными. Отсортировано по
отношению «польза инженеру / стоимость внедрения».

### 4.1. Обмер детали по фото — фотограмметрия (приоритет 1)

**Проблема.** `prompts.py:47` прямо запрещает модели брать размеры с фото:
«Use the photo for topology and feature intent, NOT for absolute dimensions».
Инженер вынужден вручную вписывать каждый размер в описание. Это главное
ограничение всего Modeling Agent.

**Что даёт L40.** Мультиракурсная съёмка детали (10–30 кадров) → COLMAP /
3D Gaussian Splatting на GPU → плотное облако точек → привязка масштаба по
эталону в кадре (линейка, калибровочная мишень, деталь известного размера) →
габариты, диаметры отверстий, межосевые расстояния.

`[оценка]` Реконструкция набора из 20 кадров: 2–5 мин на L40 против
30–90 мин на 4-ядерном CPU. Точность после масштабирования по эталону —
порядка 0,3–1 мм на детали 100 мм, чего достаточно для черновой
параметризации, но **не для допусков ±0,05 мм** из `samples/miranda-rfv-2u`.

**Как встраивается.** Новый префикс к пайплайну: результат — не геометрия, а
**таблица измерений**, которая подставляется в описание. Модель по-прежнему
пишет параметрический скрипт, но теперь на измеренных числах:

```
фото (N ракурсов) → GPU-фотограмметрия → measurements.yaml
                                          ↓
                          description + «замеренные габариты: …»
                                          ↓
                                    vision.generate_script
```

Ключевое проектное решение: **измерения идут в промпт как текст, а не как
меш**. Это сохраняет параметричность результата и оставляет инженеру
возможность поправить любое число до генерации.

### 4.2. OCR сканированных листов (приоритет 1 для BIM-контура)

**Проблема.** `docs/bim-analysis-architecture.md` фиксирует прямо: «OCR
сканированных листов пока не встроен». Лист без текстового слоя
(`pdf_index.py:28`, порог 40 символов) помечается как кандидат на визуальную
проверку, и агент вынужден читать его через `render_page` — то есть отправлять
растр в мультимодальную модель. Это дорого, медленно и не даёт координат для
`count_tag`.

**Что даёт L40.** GPU-OCR (PaddleOCR PP-OCRv4/v5, Surya, dots.ocr) выдаёт
текст **с bounding box каждого слова** — ровно та структура, которую уже ждёт
`TextSpan` (`pdf_index.py:95`). Сканированные листы попадают в тот же индекс,
что и векторные, и на них начинают работать `find_occurrences`,
`cluster_occurrences` и `count_tag` без изменения логики.

`[оценка]` Лист A1 при 300 dpi (~7000×5000 px) режется на ~35 тайлов
1280×1280: 2–5 с на GPU против 40–90 с на CPU. Комплект из 500 листов —
**25–40 минут против 8–12 часов**. Разница переводит OCR из «ночного пакета»
в «пока инженер пьёт кофе».

**Это самый чистый выигрыш во всём анализе**: закрывается задокументированная
дыра, структура данных уже готова, изменение локализовано в одном модуле.

### 4.3. Исчерпывающая проверка толщин через SDF (приоритет 2)

**Проблема.** `validator.py:65` меряет минимальную стенку выборкой из
**300 точек** с трассировкой лучей по нормалям. На детали вроде 2U-шасси с
рёбрами, направляющими и бобышками 300 случайных точек **могут не попасть в
тонкое ребро вообще** — проверка вернёт «OK» на непечатаемой модели. Это не
придирка к реализации, а свойство метода: выборка не даёт гарантии.

**Что даёт L40.** Знаковое поле расстояний (SDF) на воксельной сетке:
`[расчёт]` деталь 100 мм при шаге 0,2 мм — 500³ = 125 млн вокселей, float32 =
500 МБ, свободно помещается в 48 ГБ. `[оценка]` расчёт SDF от меша в 100 тыс.
треугольников — 1–3 с.

Результат — не одно число, а **карта толщин**: инженер видит, *где* тонко, а
не только *что* тонко. Плюс из того же поля бесплатно считаются: свесы > 45°,
объём поддержек, минимальные зазоры в сборке, интерференция между деталями.

Формально это замена «300 samples» на «полное покрытие с шагом 0,2 мм» —
переход от вероятностной проверки к детерминированной. Для gate перед печатью
это принципиально.

### 4.4. Экспресс-FEA и топологическая оптимизация (приоритет 2)

Слоя прочностного анализа в Buxter нет вообще, а инженеру-конструктору он
нужен раньше, чем красивый рендер. L40 (~90 TFLOPS FP32) тянет линейно-статику
кронштейна за секунды и топологическую оптимизацию за минуты.

Это замыкает петлю, которую README числит в планах как «self-repair loop», но
уже по **физическому**, а не синтаксическому критерию:

```
draw → validate (геометрия) → FEA (напряжения, прогиб) → retry с рёбрами
```

Практическая ценность: агент, который отвечает «кронштейн выдержит 200 Н с
запасом 1,8, максимальное напряжение в галтели у основания», качественно
отличается от агента, который просто выдал STL.

### 4.5. Детекция графических символов на чертежах (приоритет 3)

`find_occurrences` (`pdf_index.py:286`) принципиально не видит того, что не
является текстом: штриховки материалов, обозначения сварных швов, символы
разрезов, стрелки выносок. Детектор класса YOLO / RT-DETR, дообученный на
размеченном комплекте, закрывает этот класс.

`[оценка]` инференс — ~0,2 с на лист (35 тайлов); дообучение на 500
размеченных листах — 1–2 часа на L40 (48 ГБ позволяют батч 32 при 1280 px без
градиентного чекпойнтинга).

Приоритет ниже, потому что требует **разметки** — это недели работы человека,
а не настройка сервиса. Стоит начинать только после §4.2, на реальном потоке
комплектов.

### 4.6. Семантический поиск по нормам и headless-рендер (приоритет 3)

Два дешёвых пункта в одном:

- **Эмбеддинги + реранкер** (bge-m3 / multilingual-e5, ~600M параметров,
  2–3 ГБ VRAM) поверх `specs-wiki.md` и `objects-database.md`. Даёт поиск «по
  смыслу» вместо `re.escape` — запрос «защитный слой бетона для наружных
  конструкций» находит формулировку, в которой нет ни одного из этих слов.
  `[оценка]` индексация комплекта в 50 тыс. фрагментов — меньше минуты.
- **Chromium с GPU** в `browser.py`: сейчас headless-браузер рендерит WebGL
  программно через SwiftShader. Веб-вьюеры CAD (три.js-просмотрщики, облачные
  слайсеры) на этом либо еле ползут, либо отваливаются по таймауту
  `BUXTER_WEB_STEP_TIMEOUT_MS`. GPU-бэкенд убирает целый класс отказов
  Web Operator Agent.

### 4.7. Чего делать НЕ надо: генеративные 3D-модели

Отдельным пунктом, потому что это первое, что приходит в голову при виде
свободной GPU. Модели image-to-3D (TRELLIS, Hunyuan3D, TripoSR) отлично
крутятся на L40 и выдают меш за секунды.

**Они не решают инженерную задачу.** На выходе — тесселированный меш без
B-Rep, без параметров, без плоских поверхностей сопряжения, с «плавающими»
размерами. Такой результат провалит `buxter validate` по watertight и bbox, и
его нельзя отредактировать («сделай стенку 3 мм»). Промпт `prompts.py:14`
требует ровно обратного — Part-солид с именованными переменными на каждый
размер.

Допустимая ниша: **концепт-референс** на стадии обсуждения формы, наравне с
эскизом. В производственный контур — нет.

## 5. Бюджет VRAM: что реально влезает в 48 ГБ

Нужно, если решение по §3 всё же будет пересмотрено под конкретную задачу
(например, локальная модель только для черновиков или для закрытого контура).

`[расчёт]` KV-кэш на токен = 2 (K,V) × KV-головы × head_dim × 2 байта × слои.

| Модель | Веса | KV на токен | KV при 32k | Итого | Декодинг `[расчёт]` |
|---|---|---|---|---|---|
| Qwen2.5-VL-7B FP16 | 15 ГБ | 128 КБ | 4 ГБ | 19 ГБ | ~40 ток/с |
| 14B FP8 | 15 ГБ | 192 КБ | 6 ГБ | 21 ГБ | ~40 ток/с |
| 32B INT4 (AWQ) | 18 ГБ | 256 КБ | 8 ГБ | 26 ГБ | ~33 ток/с |
| 32B FP8 | 33 ГБ | 256 КБ | 8 ГБ | 41 ГБ | ~18 ток/с |
| 70B INT4 | 38 ГБ | 320 КБ | 10 ГБ | **48 ГБ — не влезает** | ~16 ток/с |

Три следствия:

1. **70B на одной L40 практически недоступна** для агентного цикла: только с
   FP8-KV-кэшем (~5 ГБ) и при одном одновременном пользователе.
2. **Длинный контекст стоит дороже весов.** `[расчёт]` 32B при 128k контекста:
   KV = 32 ГБ в FP16, то есть больше, чем сами веса в FP8. Комбинация
   «32B + 128k» вынуждает INT4-веса **и** FP8-KV. А BIM-агент растит контекст
   60 шагов подряд — это ровно тот профиль, который бьёт в это ограничение.
3. **Vision-модели на чертежах — отдельная ловушка.** Лист A1 в 150 dpi
   (`config.py:39`) для VLM с нативным разрешением даёт `[расчёт]` порядка
   20 тыс. визуальных токенов на изображение против ~1,6 тыс. у Claude,
   который ресайзит вход. Наивная замена мультимодального вызова локальным
   VLM увеличит нагрузку на контекст на порядок.

Про вторую карту: **NVLink на L40 нет**, только PCIe Gen4 x16. Считать его
пропускную способность нужно аккуратно, потому что в спецификациях обычно
приводят суммарное двунаправленное число:

`[расчёт]` PCIe 4.0 — 16 ГТ/с на линию, кодирование 128b/130b →
16 × (128/130) / 8 = 1,97 ГБ/с на линию → **31,5 ГБ/с в одну сторону** на
x16, то есть ~63 ГБ/с суммарно в обе. `[оценка]` реально достижимо
25–28 ГБ/с на pinned-памяти; при P2P между двумя GPU через корневой комплекс
— 22–26 ГБ/с, а если карты на разных root complex и P2P отключён, трафик
идёт через системную память и падает примерно вдвое.

Для tensor-parallel значимо именно **однонаправленное** число: allreduce
после каждого слоя упирается в 31,5 ГБ/с теоретических и ~25 ГБ/с
практических. Это в **~27 раз медленнее** памяти самой карты (864 ГБ/с) — и
против ~450 ГБ/с в одну сторону у NVLink на A100/H100. Отсюда вывод:
масштабировать *размер модели* двумя L40 неэффективно; две карты имеет смысл
брать только под **независимые сервисы** (одна — OCR/детекторы, другая —
геометрия/FEA), где межкарточного обмена нет вовсе.

Замечание о сопоставимости: 864 ГБ/с — это пропускная способность VRAM
внутри карты, а 31,5 ГБ/с — шина между устройствами. Величины разной
природы, и сравниваются здесь только потому, что tensor-parallel заставляет
их конкурировать в одном цикле: то, что при одной карте читается из VRAM,
при двух частично едет по PCIe.

## 6. Специфика «внешней» карты

Слово «внешняя» меняет три вещи, и их стоит развести явно.

### 6.1. Конфиденциальность: аргумент разворачивается

Обычная мотивация локальной модели — «чертежи не должны покидать периметр».
**С арендованной L40 они его покидают** — просто уезжают к другому
провайдеру, обычно с меньшими договорными гарантиями, чем у zero-retention
API.

Хуже: `[факт]` **L40 (Ada) не поддерживает Confidential Computing** — TEE и
аттестация появились только на Hopper (H100) и Blackwell. На L40 нельзя
криптографически подтвердить, что гипервизор хоста не читает содержимое VRAM.

Отсюда жёсткий вывод: если драйвер решения — коммерческая тайна, ГОСТ-контур
или NDA заказчика, то **внешняя L40 задачу не решает**, а L40 внутри периметра
— решает. Промежуточных вариантов на этом железе нет.

### 6.2. Данные: считать трафик, а не только флопсы

Комплект строительных PDF — сотни мегабайт; растр листа A1 при 300 dpi — 5–15
МБ. Гонять их между рабочей станцией и внешней картой на каждый шаг агента
бессмысленно, и здесь важно понимать порядок величин канала.

`[расчёт]` Время передачи комплекта в 300 МБ и одного растра листа в 10 МБ:

| Канал | Полезная скорость | Комплект 300 МБ | Растр листа 10 МБ |
|---|---|---|---|
| Офисный аплинк 100 Мбит/с | ~12,5 МБ/с | ~4 мин | ~0,8 с |
| Гигабит 1 Гбит/с | ~125 МБ/с | ~24 с | ~0,08 с |
| ЦОД 10 Гбит/с | ~1,25 ГБ/с | ~2,4 с | ~0,01 с |
| Для сравнения — PCIe Gen4 x16 | 31,5 ГБ/с | ~0,01 с | — |

То есть канал до внешней карты **в 25–2500 раз медленнее**, чем шина внутри
хоста. Вопрос «хватит ли PCIe» для арендованной L40 — второстепенный: узкое
место не там, а на WAN-линке, и оно на два-три порядка жёстче.

Правильная топология: **весь тяжёлый конвейер живёт на GPU-хосте**, наружу
возвращаются только артефакты (`drawings.md`, `objects-database.md`,
`measurements.yaml`, отчёт валидатора) — килобайты текста. Это, кстати, ровно
та архитектура, которую репозиторий уже подразумевает: артефакты как
контракт между слоями (`pdf_index.py:434`).

### 6.3. Утилизация: карта не должна ждать инженера

`[расчёт]` При профиле §3.3 — менее 3 % загрузки. Держать выделенную карту
24/7 под одного инженера — переплата в 30 раз.

Разумные режимы:

- **Пакетный.** Ночная индексация + OCR новых комплектов, дообучение
  детекторов, батч-валидация геометрии. Карта работает часами подряд, простой
  между задачами оплачивается только при аренде помесячно.
- **Резидентный лёгкий.** Модель 7B и OCR-сервис держатся загруженными
  постоянно (~20 ГБ VRAM) для интерактивных ответов; загрузка 32B заняла бы
  `[оценка]` 30–90 с и убила бы интерактивность.
- **Посекундная аренда.** Оправдана для §4.1 и §4.4 — фотограмметрия и FEA
  запускаются по требованию и длятся минуты.

## 7. Целевая гибридная архитектура

```
                    ┌─ КОНТУР ВОСПРИЯТИЯ И ГЕОМЕТРИИ (L40) ─┐
фото (N ракурсов) ──▶ фотограмметрия ──▶ measurements.yaml   │
PDF без текст. слоя ─▶ GPU-OCR ────────▶ TextSpan[] ─────────┼──▶ pdf_index
чертёж ─────────────▶ детектор символов ▶ Occurrence[] ──────┤
STL ────────────────▶ SDF / карта толщин ▶ отчёт валидатора ─┤
STEP ───────────────▶ экспресс-FEA ─────▶ напряжения, запас ─┤
специфик./нормы ────▶ эмбеддинги ───────▶ семантич. индекс ──┘
                                              │
                    ┌─────────────────────────┼─ КОНТУР РАССУЖДЕНИЯ (Claude API)
                    ▼                         ▼
            vision.generate_script      bim_agent / web_agent
                    │                         │
                    ▼                         ▼
            FreeCAD / Fusion (CPU)     ответ с источниками
```

Граница проведена по одному критерию: **всё, что производит измеримые факты,
идёт на L40; всё, что принимает решения на основе фактов, идёт в Claude.**

Побочный эффект такого разделения — оно же и самое дешёвое. Восприятие даёт
много вызовов по низкой цене за вызов (GPU амортизируется), рассуждение —
мало вызовов по высокой цене ошибки (платим за качество). Оптимум по деньгам
и оптимум по качеству здесь совпадают, что бывает нечасто.

## 8. План проверки: замерить, а не спорить

Главная удача ситуации в том, что **в репозитории уже есть объективная метрика
качества** — `buxter validate` возвращает ненулевой код при провале проверки.
Это позволяет сравнивать варианты машинно, а не на глаз.

### 8.1. Золотой набор для CAD-контура

Собрать 20 задач с известным ответом (кронштейны, корпуса, детали из
`samples/miranda-rfv-2u`), для каждой зафиксировать ожидаемый bbox и
минимальную стенку. Прогнать каждую конфигурацию по 3 раза:

```bash
for task in golden/*.txt; do
  buxter draw -d "$(cat $task)" -o out/$(basename $task .txt)/ \
    && buxter validate out/$(basename $task .txt)/out.stl \
         --min-wall 1.6 --expect-bbox "$(cat golden/$(basename $task .txt).bbox)"
done
```

Метрики: доля прошедших gate, доля скриптов, упавших в `freecadcmd`, число
итераций `retry` до успеха, wall-clock и стоимость на успешную деталь.

Конфигурации к сравнению: Claude Opus, Claude Sonnet, локальная 32B FP8,
локальная 32B INT4, локальная 14B. **Решение по §3 принимается по этой
таблице, а не по настоящему документу** — здесь гипотеза, там измерение.

### 8.2. Золотой набор для BIM-контура

10–15 вопросов по комплекту с проверенными вручную ответами. Метрика — не
только точность числа, но и **корректность калибровки надёжности**: ответ
«120 м³, reliability High» при верных 95 м³ хуже, чем «около 100 м³,
reliability Low». Отдельно замерить долю листов, на которых GPU-OCR даёт
`TextSpan`, пригодные для `count_tag`.

### 8.3. Что мерить на самой карте

Прежде чем считать экономику — снять реальные числа вместо `[оценка]`:
токены/с на декодинге и prefill при трёх размерах модели, страниц/с у OCR на
реальных листах A1, время SDF на реальном STL из `out/`, время реконструкции
на реальной съёмке детали. Все прикидки этого документа помечены и подлежат
замене.

## 9. Точки интеграции в коде

Оценка трудозатрат для гибридного варианта (§7). Важно: **ни один пункт не
требует переписывания архитектуры** — слои Buxter уже развязаны артефактами.

| Что | Где | Изменение | `[оценка]` объём |
|---|---|---|---|
| GPU-OCR листов | `pdf_index.py:173` | ветка: нет текстового слоя → HTTP-вызов OCR-сервиса → те же `TextSpan` | 2–3 дня |
| SDF-валидация | `validator.py:126` | новый чекер рядом с ray-выборкой, флаг `--exhaustive` | 3–5 дней |
| Фотограмметрия | новый модуль + `cli.py` | команда `buxter measure`, выход — `measurements.yaml` в описание | 1–2 недели |
| Экспресс-FEA | новый слой | `buxter analyze` поверх STEP, отчёт в тот же формат `Check` | 2–3 недели |
| Семантический поиск | `bim_agent.py:40` | новый tool `search_semantic` рядом с `search_text` | 3–4 дня |
| GPU-Chromium | `browser.py:113` | флаги запуска + `BUXTER_WEB_GPU` | 1 день |

Отдельно про **локальную модель**, если она всё же понадобится для закрытого
контура: `vision.py:136` жёстко завязан на `anthropic.messages.create`.
Замена одного вызова на OpenAI-совместимый эндпоинт vLLM — полдня. Но
`web_agent.py:236` и `bim_agent.py:577` используют tool-use блоки Anthropic,
которые **не мапятся один в один** на OpenAI-формат (различия в структуре
`tool_result`, в обработке параллельных вызовов и в блоках изображений). Это
адаптер на `[оценка]` 3–5 дней плюс регрессия на золотом наборе §8.

Порядок внедрения диктуется отношением «польза / риск»:

1. **GPU-OCR** — закрывает задокументированную дыру, структура данных готова.
2. **SDF-валидация** — превращает вероятностный gate в детерминированный.
3. **Фотограмметрия** — снимает главное ограничение Modeling Agent.
4. **FEA** — новая ценность для конструктора, но и новый слой целиком.
5. Детекторы символов и семантический поиск — после того, как накопится
   поток реальных комплектов.

## 10. Решение

| Вопрос | Ответ |
|---|---|
| Ставить ли LLM Buxter на внешнюю L40? | **Нет.** Хуже по качеству, медленнее по wall-clock, дороже при 1–2 инженерах (§3). |
| Полезна ли L40 для Buxter вообще? | **Да**, в контуре восприятия и геометрии — и там она даёт не ускорение, а функции, которых сейчас нет (§4). |
| Решает ли внешняя L40 вопрос конфиденциальности? | **Нет.** Данные всё равно вне периметра, а Confidential Computing на Ada отсутствует (§6.1). Для закрытого контура нужна карта внутри периметра. |
| Что делать первым? | GPU-OCR сканированных листов (§4.2) — минимальный риск, максимальный эффект. |
| Что даст больше всего инженеру-конструктору? | Фотограмметрический обмер (§4.1): фото перестаёт быть подсказкой о форме и становится источником размеров. |
| Как принять окончательное решение по §3? | Прогнать золотой набор через `buxter validate` (§8.1) и заменить оценки замерами. |

Ключевая мысль, если оставить одну: **L40 не должна пытаться думать за Claude
— она должна давать Claude факты, которых у него сейчас нет.** Агент,
рассуждающий по обмеренной геометрии, распознанным сканам и исчерпывающей
карте толщин, сильнее агента, который рассуждает по описанию, — независимо от
того, какая модель рассуждает.
